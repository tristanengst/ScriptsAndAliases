# Workstation SLURM: setup

How the non-root SLURM is installed and run, how to add a machine, and what each file does. How it
behaves for jobs: `README.md`. Background: `~/SLURMSetup.md` (design), `~/SLURMSetupProgress.md`
(what was tested on A99 and what was learned). A99 is set up and is the controller. All hostnames
are in `../Private/SLURM/`, since they can't be public.

Every machine is both a **compute node** (runs `slurmd`) and a **login node** (can run `sbatch`,
`squeue`, etc.). Only the controller also runs `slurmctld`.

**Homes are not shared, and are in different places on different machines** (eg. under `/home`
on A99, under `/localscratch` on S1). The only shared filesystem is `/NAS`. Never write
`/home/...`: use `$HOME`/`~` in scripts, and `${HOME}` in `slurm.conf.in` (filled in per node by
`bin/render_config`). Scripts that SLURM runs, which have no `HOME` (or the submitting machine's),
read it from the machine's node file, which `add_node` writes from `$HOME`. This is also why
SLURM is built separately on each machine, and why its installed munge key and SLURM state live
in each machine's own `~/.local/slurm`.

Machines don't need identical installs, only ones that interoperate: the same SLURM version
(pinned and checksummed in `build.sh`), the same munge key and the same config. Everything comes
from the repo and its Private submodule (config templates, node files, the munge key,
`gpu_names`, scripts, `crontab`, `build.sh`), and per-machine values are generated by scripts
(`add_node`, `render_config`), not written by hand. Each machine's cron (`bin/start_daemons`,
every minute) makes its SLURM match what it has checked out, so a change takes effect on a
machine within a minute of pulling it there.

**The controller is just a machine named as `SlurmctldHost`** in `Private/SLURM/slurm.conf`.
Every machine is set up the same way (`setup_node`), and the one named there runs `slurmctld`.
Nothing about a node depends on which machine is the controller, or on the controller being
reachable while setting it up.

**Users are matched by name, not by uid:** see "Users and uids" below.

**The munge key** (the secret every machine's `munged` uses to sign and check SLURM's messages)
is shared by all machines: one file, `Private/SLURM/munge.key`, which `start_daemons` installs as
`~/.local/slurm/etc/munge/munge.key`. Its origin is recorded in `Private/SLURM/README.md`.

## Setting up the controller

The first machine, or a replacement for a controller that died.

1. **Prerequisites** on the machine (once): as for adding a machine, below.
2. **For a new cluster only**, make the munge key (once, ever): `mungekey -c -k
   ~/.ScriptsAndAliases/Private/SLURM/munge.key`, and note in `Private/SLURM/README.md` where
   and when it was made. (Replacing a controller keeps the existing key.)
3. **Name it the controller:** set `SlurmctldHost=<its hostname -s>` in
   `Private/SLURM/slurm.conf`.
4. **Set it up as a machine** (below, step 2 on): `setup_node`, commit and push, pull everywhere.
   Within a minute of pulling, it starts `slurmctld`, every other machine's slurmd rereads the
   config and reports to it, and a previous controller that's still up stops its `slurmctld`.

Replacing a controller loses the queue: `slurmctld` keeps it in `~/.local/slurm/var/state/` on
the old controller. Jobs still pending there are gone, jobs still running are killed when their
machines report to the new controller, and job numbers start again from 1. To keep the queue
when moving a controller that's still up, first stop its `slurmctld` and copy that directory to
the new controller's `~/.local/slurm/var/state/`.

## Adding a machine

`NODE` is the new machine's `hostname -s`.

1. **Prerequisites** (once; `setup_node` can't do these):
   - `~/.ScriptsAndAliases` is cloned and up to date, with the Private submodule checked out, and
     conda is installed (`build.sh` finds it through `$CONDA_EXE`, `conda` on PATH, or
     `~/miniconda3`, `~/miniforge3`, `~/anaconda3`).
   - `sudo` on the machine: `setup_node` uses it to open SLURM's ports automatically (what it
     does: Ports, below).
2. **On NODE:** `~/.ScriptsAndAliases/SLURM/bin/setup_node --gpus all` (or `none`, or the
   nvidia-smi indices SLURM gets, eg. `--gpus 0,2`; the rest stay outside SLURM). It:
   - checks the clock, crontab, that the ports are free and that the controller resolves;
   - opens SLURM's ports in `ufw` (with `sudo`) to the lab's machines (`MachineHostnames.py`);
   - builds SLURM if the installed build isn't `build.sh`'s (~5 min);
   - writes the node file `Private/SLURM/nodes/NODE.conf` (`bin/add_node`: home from `$HOME`,
     CPU layout and memory from `slurmd -C`, GPUs from nvidia-smi, feature = the GPU model's
     name, derived from nvidia-smi's, eg. `rtx_2080_super`) and, if it has none, its GPU-CPU map
     (`cpus:` lines, from the CPU topology; check them, and edit them if needed);
   - adds the SLURM lines to the crontab (other lines are kept);
   - runs `start_daemons` (config, munge key, daemons), and checks (`scontrol ping`) that the
     controller accepts this machine's munge key, and that the SLURM versions match.

   It ends with warnings to commit the node file and that the controller doesn't know NODE yet.
3. **Commit and push** `nodes/NODE.conf` in the Private repo, then the submodule update in
   `~/.ScriptsAndAliases`.
4. **`git pull` (and `git submodule update`) on every machine.** Within a minute, each one's cron
   re-renders its config with NODE in it and its daemons reread it. (If NODE is new to
   `Private/MachineHostnames.py` too, rerun `setup_node` on every other machine, so their
   firewalls let it in.)
5. **On NODE:** `update_scripts_and_aliases`, then `setup_node` again with no arguments: it should
   end with "0 warnings" and NODE `idle`.
6. **Check** from a new shell on NODE:
   - `cd /NAS/$USER; srun -w NODE --gpus-per-node=1 bash -c 'echo $CUDA_VISIBLE_DEVICES; nvidia-smi -L'`:
     a GPU UUID of one of the GPUs given to SLURM.
   - `sbatch` from NODE to the controller and back (`-w`).
   - `squeue -n blocking_job_NODE_0` (etc.): one held blocker per GPU, within a minute.
   - Blocker cycle: run a CUDA process on one of those GPUs outside SLURM; within ~30 s its
     blocker runs; stop it; within ~30 s the blocker is held again. (`~/SLURMSetupProgress.md` has
     the test helper.)

## Users and uids

**The issue.** Each machine has its own accounts, so the same user has a different uid on
different machines. Stock SLURM assumes a user's uid is the same everywhere: munge signs
every message with the sender's numeric uid, and SLURM compares uids to decide who someone is.
With different uids, the machines reject each other ("Security violation ... from uid 1006",
"cred/munge: Unexpected uid"), jobs submitted from one machine belong to a nonexistent user on
the controller, and `squeue`/`scancel -u` match nothing from other machines.

**The patch.** `build.sh` applies `patches/user-by-name.patch`, under which a user *is* their
user name, and a uid is only that name's number on one machine:
- Where SLURM needs a number, it uses the local one: every signed message carries the sender's
  user name, which the receiver turns into its own uid and groups; a machine running a job runs
  it as the job's user name's local uid; a uid a client sends as "me" (eg. when `srun` starts a
  step) is replaced by the sender's, as SLURM already does for job submission.
- Where SLURM matches users, it compares names: `squeue -u`/`--me`/`--notme` and
  `scancel -u`/`--me` work from any machine. slurmctld sends every job's user name (stock SLURM
  only sets it once a job starts).
- Where SLURM shows users, it shows the name sent: `squeue`'s `USER` and `scontrol show job`'s
  `UserId=`. Otherwise another machine shows slurmctld's uid under its own name for that
  number: on A4, uid 1006 (`tme3` on A99) is a different person.

The alternative, giving the user the same uid on every machine (`sudo usermod -u`, then
re-owning files outside the home directory), needs no patch, but changes accounts on shared
machines.

**What the patch doesn't fix:**
- `squeue -s -u` (job steps by user) still matches by number, since SLURM's step listing has no
  user name: it only works on the controller's machine.
- Numbers SLURM shows or passes on can be another machine's: eg. the `1006` in `scontrol show
  job`'s `UserId=tme3(1006)` is the controller's uid, and `SLURM_JOB_UID` in the Prolog and
  Epilog may be too. Use user names (`SLURM_JOB_USER`, `id -un`), never uids.
- `squeue --json` (and other JSON/YAML output) and `squeue -s` (steps) still name users by
  looking up the number on the machine they run on, so on another machine they can show someone
  else's name.
- Options that take a uid number (eg. `squeue -u 1006`) mean that number on the machine they're
  run on.
- Every machine must run the patched build (`setup_node` rebuilds when the patch changes): a
  patched and an unpatched machine still disagree, as above.
- It relies on munged's socket being reachable only by the user running SLURM (it's under
  `~/.local/slurm`, not readable by others): anyone who could use it could claim any user name.
- SLURM features not used here (accounting, `sbcast`, X11 forwarding, reservations by user)
  weren't checked, and may still compare uids.

The same list is at the top of the patch file. Without the patch, uids must match on every
machine; groups needn't (without root, SLURM never switches a job's group).

## Ports

**`setup_node` handles the ports automatically; nothing needs doing by hand on a machine with
`ufw`.** This section says what it does, so it can be checked, or done by hand where it can't
(another firewall, or `setup_node` couldn't run `sudo`):

- With `ufw` enabled: asks for the `sudo` password (run it in a terminal), then lets the lab's
  machines in to SLURM's ports and removes its stale rules (details below).
- With `ufw` installed but disabled (eg. A99): nothing to do; it says "ufw inactive".
- Without `ufw`: it warns, listing the ports and addresses another firewall must let in.

Which ports SLURM uses is set in `Private/SLURM/slurm.conf` (`SlurmctldPort`: slurmctld, on the
controller; `SlurmdPort`: slurmd, on every machine; `SrunPortRange`: srun, on the machine running
it, for its tasks' I/O and status). `setup_node` opens all of them on every machine (so any
machine can become the controller) in `ufw`, Ubuntu's firewall, with `sudo`, but only to the
lab's machines: those in `Private/MachineHostnames.py`, whether or not they're in SLURM (so
adding a machine to SLURM never needs a firewall change elsewhere). Each hostname there that
resolves gets one rule per address it resolves to when `setup_node` runs. It also removes its
old rules (comment `workstation SLURM`) for addresses or ports no longer wanted. Firewall rules
need root, so cron can't keep them up to date: **when a machine is added to
`MachineHostnames.py`, or one's address changes, rerun `setup_node` on every machine in SLURM.**

By hand, or for another firewall (the same rules in its own terms), for each address `ADDR` of
each machine in `MachineHostnames.py`:

```bash
# SLURM's ports from Private/SLURM/slurm.conf
eval "$(sed -n 's/#.*//; s/^SlurmctldPort= *\([0-9]*\).*/ctld_port=\1/p; s/^SlurmdPort= *\([0-9]*\).*/slurmd_port=\1/p; s/^SrunPortRange= *\([0-9]*\)-\([0-9]*\).*/srun_lo=\1 srun_hi=\2/p' ~/.ScriptsAndAliases/Private/SLURM/slurm.conf)"
# Let ADDR in to them (rerunning doesn't duplicate the rule)
sudo ufw allow proto tcp from ADDR to any port "$ctld_port,$slurmd_port,$srun_lo:$srun_hi" comment 'workstation SLURM'
```

Beyond that, security is munge, the way it's ssh keys for ssh: every SLURM message must be
signed with the shared munge key (`Private/SLURM/munge.key`), and the daemons drop anything that
isn't, so only holders of the key can get SLURM to do anything. (Messages are signed, not
encrypted: job I/O that srun relays crosses the network readable.)

A firewall between networks that the department runs isn't covered by this. To check the ports
between machines, with the variables above: `CTLD` is the controller, `OTHER` any machine already
in SLURM. Each `nc -zv` should print "succeeded":

```bash
# On NODE, to machines already running SLURM (their daemons are listening):
nc -zv -w 3 CTLD $ctld_port      # slurmctld: every machine sends it jobs, queries, job results
nc -zv -w 3 OTHER $slurmd_port   # slurmd: the controller (and srun) start jobs through it
# Into NODE (before its daemons run, nc listens in their place; Ctrl-C after):
nc -l $slurmd_port               # on NODE: stands in for its slurmd
nc -zv -w 3 NODE $slurmd_port    # on CTLD
nc -l $srun_lo                   # on NODE: stands in for srun, which listens in
                                 #   SrunPortRange for its tasks, from whichever machines run them
nc -zv -w 3 NODE $srun_lo        # on OTHER
```

`setup_node`'s `scontrol ping` check also tests `SlurmctldPort` from each machine.

## Tunnels

**The issue.** The department's network lets ssh through between all the lab's machines, but not
SLURM's ports in every direction. Tested on 2026-10-27:

| From → to | ssh | SLURM's ports |
|---|---|---|
| anywhere → workstations | yes | yes |
| servers (S1–S3) → each other | yes | yes |
| workstations → S1–S3 | yes | no (only 8080 got through) |
| workstations, S1–S3 → V21 | yes (V21: port 24) | no |
| V21 → anywhere | yes | yes |

So the controller (a workstation, which everyone can reach) can't reach slurmd on S1–S3 or V21.

**The fix.** A machine the controller can't reach directly has `tunnel_port=P` in its node file,
set by hand (P: unique among the node files; 46901 and up). Then:
- `bin/start_daemons` on that machine (cron, every minute) keeps one ssh connection to the
  controller running, with a reverse forward: the controller's `127.0.0.1:P` reaches this
  machine's slurmd. It's an ssh process of its own (no connection sharing), restarted within a
  minute if it dies, and moved if `SlurmctldHost` changes. Log: `~/.local/slurm/var/log/tunnel.log`.
- `bin/render_config` on the controller lists that machine as `NodeAddr=127.0.0.1 Port=P`; every
  other machine's config, and the machine's own slurmd port, are unchanged.
- `TreeWidth` is high, so the controller contacts every slurmd itself instead of relaying
  through other machines.

This needs every tunnelled machine to ssh to the controller without a password (`ssh-copy-id`),
which `setup_node` checks. Everything else reaches the controller directly.

**What works:** batch jobs on and from every machine, `srun` inside jobs, and every query
command (`squeue`, `scancel`, `scontrol`, `sinfo`) from every machine.

**What doesn't:** interactive `srun`/`salloc` between machines the network separates (eg. from a
workstation onto S1: it hangs). SLURM sends those machine to machine, not through the
controller. Also `salloc`/`srun` started on a tunnelled machine may not hear the controller's
callbacks (allocation ready, time limits). Use `sbatch` there, or run interactively from a
machine on the same side.

If the department opens SLURM's ports, delete the `tunnel_port=` lines: nothing else changes.

## Maintenance

Rerun `setup_node` any time to check a machine; it only changes what's missing or out of date.
After hardware changes, rerun it with `--gpus`. After changing `slurm.conf.in`, `gres.conf.in`,
`cgroup.conf`, `gpu_names` or anything in `Private/SLURM/` (including the munge key): push and
pull everywhere; each machine applies it within a minute. When a machine's address changes, a
machine is added to `Private/MachineHostnames.py`, or after changing the ports: rerun
`setup_node` on every machine (firewall rules). After changing the SLURM version in
`build.sh` or a patch: push, pull, and `setup_node` on every machine rebuilds and restarts its
daemons (running jobs survive). Until every machine has the new build, machines with different
builds may not understand each other. Cron restarts a daemon that stops within a minute, so to stop SLURM on a
machine, first remove its SLURM crontab lines (`crontab -e`).

Logs: `~/.local/slurm/var/log/` (`slurmd.log`, `slurmctld.log` on the controller, `cron.log`,
`blocker_cron.log`, `task_prolog.log`, `sweep_tmpdirs.log`, `prolog.log`) and
`~/.local/slurm/var/log/munge/munged.log`.

# Files

Paths are relative to this folder, `SLURM/` (public); `../Private/SLURM/` is private (hostnames).

### Core SLURM configuration

What's normally `/etc/slurm/`, the same for every machine.

- `slurm.conf.in`, `gres.conf.in`, `cgroup.conf`: templates. Every GPU is its own GRES type
  `gN` = `/dev/nvidiaN`, so a blocker can hold one GPU.
- `../Private/SLURM/slurm.conf`: the site's private lines (`SlurmctldHost`, the controller).
- `../Private/SLURM/munge.key`: the munge key, shared by every machine.
- `bin/render_config`: writes the config to `~/.local/slurm/etc/` on each machine, filling in
  `${HOME}`, `${USER}` and `${SLURM_DIR}` and adding the private lines and every machine's node
  lines (below). Run by `start_daemons`.

### How SLURM sees each machine

- `../Private/SLURM/nodes/<host>.conf`: one per machine, its node file: its home (`home=`, for
  scripts SLURM runs without a `HOME`), its `slurm.conf` node line (`slurm:`), its `gres.conf`
  lines (`gres:`) and its GPU-CPU map (`cpus: <GPU index> <CPUs>`, one per GPU, including ones
  left out of SLURM).
- `bin/add_node`: writes this machine's node file from `$HOME`, `slurmd -C`, nvidia-smi and the
  CPU topology (run by `setup_node`). The `cpus:` lines are only written if the file has none (or
  with `--reset-cpus`), so hand edits are kept. As written, each NUMA node's cores are split
  evenly over the GPUs attached to it, the last getting any left over, hyperthreads of a core
  together. On S1-S3 that's exactly `TorchRun.py`'s hand-written map (checked on S1), and in
  principle on V21 (not reachable to check).
- `gpu_names`: renames the GPU model feature names `add_node` derives (eg. `rtx_2080_super`).

### Making a machine available

- `bin/setup_node`: sets up or re-checks a machine (above): checks, build, node file, munge key,
  crontab, daemons.
- `build.sh`: builds SLURM into `~/.local/slurm`: a pinned, checksummed SLURM version with
  `patches/*.patch` applied; conda-forge compilers with a glibc 2.28 sysroot; munge, json-c, lz4
  and readline from conda-forge, unpinned. Per machine, since `$HOME` paths are compiled in;
  machines only need the same build (`build.sh --version`: the SLURM version and a hash of the
  patches, recorded in `~/.local/slurm/.slurm_build`).
- `patches/user-by-name.patch`: makes SLURM match users by name, not uid (above).
- `crontab`: the SLURM crontab lines, merged into the user's crontab by `setup_node`.
- `env.sh`: puts SLURM on PATH. Sourced by `~/.bashrc` and everything in `bin/`; scripts SLURM
  runs (no `HOME`, or the submitting machine's) pass `--node-home` to take it from the node file.

### Run as part of jobs

Set in `slurm.conf.in`; SLURM runs them on the machine running the job.

- `bin/prolog`: once per job, before any of its tasks. Points `/tmp/$USER-home` at the machine's
  home (`ln -sfT`; fails, draining the node, if someone else made that path), and makes an empty
  `SLURM_TMPDIR` (`~/slurm_tmpdirs/job_<id>`).
- `bin/task_prolog`: before each task, fixes `HOME` and `PATH` for the machine, sets
  `SLURM_TMPDIR`, rewrites `CUDA_VISIBLE_DEVICES` to GPU UUIDs (SLURM without cgroups gives the
  position in `gres.conf`, not the device number), hides GPUs from jobs without any, and pins the
  task to its GPUs' CPUs from the node file's `cpus:` lines (`taskset -p` on its parent, the task
  process, which then becomes the job's program). Before a job's first task, fails it if its
  directory doesn't exist here (SLURM would run it in `/tmp`), and requeues it (batch) or cancels
  it (srun/salloc) if one of its GPUs is busy outside SLURM.
- `bin/epilog`: once per job, after it ends. Removes its `SLURM_TMPDIR`.

### Managing SLURM on each machine

Run by cron (`crontab`).

- `bin/start_daemons` (every minute): makes this machine's SLURM match the repo. Renders the
  config, installs the munge key (restarting munged if it changed), starts munged, slurmd, and
  slurmctld if this is `SlurmctldHost` (stopping it if not), and tells running daemons to reread
  the config if it changed (`SIGHUP`; running jobs are unaffected). So after a reboot or a crash,
  daemons are back within a minute.
- `bin/blocker_cron` (every 30 s): for each of this machine's GPUs in SLURM, keeps a held blocker
  job `blocking_job_<node>_<N>`, and releases it when the GPU is used outside SLURM.
  `bin/blocker.sh` is the blocker job itself: it holds the GPU until it's free again, then
  requeues itself held. `bin/gpu_busy_outside` tells whether a GPU is in use outside SLURM (a GPU
  process is SLURM's if a `slurmstepd` is among its ancestors); `task_prolog` uses it too.
- `bin/sweep_tmpdirs` (every minute): removes `SLURM_TMPDIR`s the Epilog missed (eg. after a
  crash): only those whose job neither the controller nor this machine's slurmstepds have running
  here, under a lock the Prolog also takes. Deletes nothing if either can't be asked.

### On each machine, outside the repo

`~/.local/slurm/` (SLURM itself, `etc/` rendered config and munge key, `var/` state and logs),
`~/.local/slurm-build/` (compilers and source), `~/slurm_tmpdirs/`, `/tmp/$USER-home`.
